# Passenger composition labels across all trip/transfer messages

Two global helpers in `app/Helpers/functions.php` — `pax_label($pax, $fallbackTotal)` for trips and `transfer_pax_label($adults, $children, $infants)` for transfers — replace the old "N passageiro(s)" text everywhere the system talks to a customer or admin (WhatsApp, vouchers, emails, cart, checkout summary, admin screens). Trip labels are built from the `booking_items.pax` category map (`{traveler_category_id: qty}`, stored as JSON), resolving category names once per request from `traveler_categories`. Transfer labels are built from the `adults`/`children`/`infants` columns. The change also removes the old `booking_travelers`-driven passenger line in the admin booking view in favor of the pax map.

Watch for: the trip fallback `total_pax` no longer exists on persisted rows (`getItems()` returns `bi.*`, no `total_pax`) — harmless today because `pax` is always populated, but it means the fallback silently degrades to "1 passageiro" if `pax` is ever empty (confirmed). `pluralize_category` uses a two-rule heuristic that mispluralizes any admin-created category not ending in a vowel or `-l` (possible). `transfer_pax_label` hardcodes "infantil" for the third slot while trip labels use DB category names, so the same traveler type can read differently across message types (possible).

**Verdict**: APPROVED

## High-level view

The trip path is data-consistent. Every producer of a trip pax value feeds `pax_label` the real `{cat_id:qty}` map: pre-persistence it's a PHP array from the cart session, post-persistence it's the JSON string straight off `booking_items.pax` (`SELECT bi.*`). `pax_label` accepts both and decodes the string, so cart, checkout, admin, voucher, and email paths all render composition correctly.

The fallback is structurally correct but its input is dead. `pax_label` only uses `$fallbackTotal` when the category map is empty; whenever quantities exist they win. Every post-persistence call passes `(int)($item['total_pax'] ?? 1)`, and `total_pax` does not exist on those rows, so the fallback is effectively the literal `1`. This is invisible in normal flow because `booking_items.pax` is always written via `json_encode($tripItem['pax'])`, but any row with an empty/`"[]"` pax would print "1 passageiro" regardless of the real count.

Transfers are driven by three integer columns that are always set at insert time (`adults` defaults to 1, children/infants to 0), so `transfer_pax_label` gets real values everywhere. The `0 passageiros` edge only triggers if all three are zero, which the checkout insert path prevents.

The pluralization heuristic is the weakest point. It handles the four seeded categories (Adulto, Criança, Bebê, Idoso) correctly, but it's a guess for any category an operator adds later, and it can't know that a trip category named "Bebê" and a transfer's "infantil" slot mean the same thing.

The admin booking view now always renders a Passageiros line from the pax map instead of conditionally rendering from `booking_travelers`. This is an improvement in reliability (pax is always present; traveler names often aren't) but changes what's shown from named travelers to a category count.

### Trip pax data is consistent at every call site (confirmed)

Two shapes reach `pax_label`, and both are handled. In the cart session path — `resources/views/frontend/cart/index.php:37`, `resources/views/frontend/checkout/index.php:270` and `:386` — `$item['pax']` is the PHP array `['category_id' => qty]` set in `CartController::add` (`app/Controllers/Frontend/CartController.php:228`, `'pax' => $pax`). In every post-persistence path — `CheckoutController::notifyAdminNewBooking` (`:649`), `VoucherService` trip caption (`app/Services/VoucherService.php:398`), `resources/views/admin/bookings/show.php:193`, `resources/views/vouchers/trip-voucher.php:112`, `resources/views/emails/admin-notification.php:38` — the value is the raw `booking_items.pax` JSON string, because `Booking::getItems` and the VoucherService queries all select `bi.*` (`app/Models/Booking.php:42`, `app/Services/VoucherService.php:59` and `:366`). `pax_label` decodes strings via `json_decode(..., true)` and falls back to `[]` on non-arrays, so both shapes render the composition.

The write side confirms the map is always present: `CheckoutController` persists `'pax' => json_encode($tripItem['pax'])` (`app/Controllers/Frontend/CheckoutController.php:256`) unconditionally for every trip item, and the cart item always carries `pax` from user input keyed by category id.

### The trip fallback argument is dead code (confirmed)

`pax_label` only consults `$fallbackTotal` when the summed category quantities are zero. Every post-persistence caller passes `(int)($item['total_pax'] ?? 1)`, but `total_pax` is not a `booking_items` column and is not aliased in any `getItems()`/voucher query — it exists only on the *cart* item (`CartController.php:235`, `'total_pax' => $calculation['total_pax']`). So on persisted rows the expression always evaluates to `1`.

```php
// functions.php — fallback only runs when the map is empty
if ($total === 0) {
    $total = max(0, $fallbackTotal);      // = 1 on persisted rows
    return $total . ' ' . ($total === 1 ? 'passageiro' : 'passageiros');
}
```

This never surfaces in practice because `booking_items.pax` is always a non-empty JSON object for real bookings, so `$total` is never zero on those rows. The concrete risk: a booking item whose `pax` decodes to `[]` or `{}` (bad legacy data, a future code path that writes an empty map) would print "1 passageiro" — a plausible-looking but wrong count that masks the problem rather than showing "0". If you want the fallback to be meaningful post-persistence, pass a real total (e.g. the sum of the decoded pax, or the count of `booking_travelers`) instead of the non-existent `total_pax`.

### `pluralize_category` is a two-rule heuristic (possible)

```php
if (mb_substr($lower, -1) === 'l') return mb_substr($name, 0, -1) . 'is';  // infantil -> infantis
return $name . 's';
```

For the seeded set this is correct: Adulto→Adultos, Criança→Crianças, Bebê→Bebês, Idoso→Idosos (seeds at `database/seeds.sql:20-23`). The rule breaks for categories an operator could add later where Portuguese plurals aren't "+s": names ending in -m (viagem→viagens, not viagems), -r/-z/-s, or names already stored in the plural (which would get a spurious trailing s). Since the four defaults cover the shipped product and there's no traveler-category CRUD in the admin controllers I could find, this is a latent risk rather than a live bug — worth a plural column or explicit map if custom categories are ever exposed.

### Transfer labels use a fixed vocabulary, trips use DB names (possible)

`transfer_pax_label` hardcodes adulto/criança/infantil for its three columns, while `pax_label` prints whatever `traveler_categories.name` holds. A trip booked with the "Bebê" category renders "1 bebê" while the transfer leg of the same order renders "1 infantil" for the equivalent slot. Purely cosmetic, but it's a cross-message inconsistency for the same customer. Note also the transfer columns are a fixed 3-way split, so a transfer can never express categories like "Idoso" — that's a pre-existing data-model limit, not introduced here.

### transfer-confirmation default change (possible)

`resources/views/emails/transfer-confirmation.php` (three blocks, lines 116/168/214) previously rendered `(int)($tr['adults'] ?? 1)` and now passes `$tr['adults'] ?? 0` into the helper. If a transfer row had zero/absent adults the email would now read "0 passageiros" instead of the old "1 adulto(s)". The checkout insert path writes `'adults' => (int)($transfer['adults'] ?? 1)` (`CheckoutController.php` transfer insert), so live rows always have `adults >= 1` and this won't trigger — flagged for completeness.

### Admin booking view: unconditional Passageiros line (confirmed)

`resources/views/admin/bookings/show.php` dropped the `if (!empty($item['travelers']))` wrapper and the loop over `$item['travelers']` (named travelers from `booking_travelers`), replacing it with `pax_label($item['pax'] ...)`. This is more reliable: `booking_travelers` rows are only inserted when the customer supplied a name (`CheckoutController.php` traveler loop guards on `!empty($traveler['name'])`), whereas `pax` is always written. Two side effects: the displayed content changes from named categories to an aggregate count, and `BookingsController::show` still populates `$item['travelers']` (`app/Controllers/Admin/BookingsController.php:83`) which is now unused on this view — harmless, a small dead-load.

### Helper availability (confirmed, no issue)

`app/Helpers/functions.php` is required unconditionally in the front controller `public/index.php:52`, before routing. Every new call site is reached inside a normal HTTP request (frontend/admin controllers, views rendered via `View::render`, and the request-scoped `VoucherService`/`WhatsAppService`). No CLI/cron/worker entrypoint invokes these helpers or the voucher/WhatsApp services outside that bootstrap, so the globals are always defined. `pax_label`'s category lookup goes through `\Core\Database::getInstance()` inside a try/catch that degrades to an empty map (labels fall back to "Passageiro") if the DB is unreachable.
