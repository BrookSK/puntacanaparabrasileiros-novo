# SEO metadata, sitemap/robots, and delivery hardening for the tourism site

Adds a self-contained SEO layer to the PHP MVC site: new view helpers that emit description/canonical/Open Graph/Twitter/robots tags and JSON-LD, a global `TravelAgency` organization block plus per-page structured data, a dynamic `SeoController` serving `/sitemap.xml` and `/robots.txt`, Product + BreadcrumbList JSON-LD on the trip detail page, automatic Google Analytics injection from settings, and `.htaccess` changes for HTTPS redirect, gzip, and cache headers. The approach centralizes head metadata in `seo_meta_tags()` and drives it from view variables that controllers already pass (`pageTitle`, `metaDescription`), with `??` guards so views that don't set them still render. All new settings keys the code reads (`site_url`, `google_analytics_id`, `site_name`, `meta_description`) exist in `seeds.sql` with `autoload` defaulting to 1, and every sitemap query targets a column that exists in the schema.

Watch for: the `<title>` and the Open Graph title are built by two independent code paths that append the brand differently — the OG/Twitter title can end up double-branded even when the visible `<title>` is deduped (confirmed). The HTTPS redirect is correct for proxied production but forces HTTPS on every environment including local http, so a local Apache without a cert will break unless it also sends `X-Forwarded-Proto: https` or the rule is scoped (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The head refactor moves all metadata into `seo_meta_tags()` and fixes the old duplicated-brand `<title>`. The visible title is deduped in the layout, but `seo_meta_tags()` re-derives its own `fullTitle` from the raw title, so the two can disagree and OG/Twitter can carry a doubled brand. Missing per-page view variables are handled with `??`, so pages that never set `pageTitle`/`jsonLd` render cleanly.

The `.htaccess` HTTPS redirect uses `X-Forwarded-Proto` to avoid the classic proxy redirect loop, which is the right instinct and works behind a load balancer that terminates TLS. The remaining exposure is non-production http (local dev, plain http staging): the rule fires there too and will 301 to an https URL the server may not serve.

The sitemap and robots controller reads only columns that exist in the schema, wraps each dynamic query in a `try/catch` so a missing table degrades to a smaller-but-valid sitemap, and echoes XML directly with an early `exit`. It relies on the front controller forwarding `.xml`/`.txt` paths to `index.php`, which the existing rewrite does since those virtual paths aren't real files.

The trip Product JSON-LD gates `offers` on a positive price and `aggregateRating` on both a rating and a review count, so it won't emit the invalid "rating with no reviews" schema that Google rejects. Google Analytics only renders when the ID setting is non-empty. The organization JSON-LD hardcodes phone and social links rather than reading settings.

<details>
<summary>Issues (6)</summary>

1. **OG/Twitter title double-branding** — the layout dedupes the brand for `<title>` but `seo_meta_tags()` independently appends `| siteName` to the raw `title`, so a page whose title already contains the brand gets a doubled brand in `og:title`/`twitter:title`. Pass the already-deduped `$seoFullTitle` into the helper (and have the helper use it verbatim), or move the dedup into the helper and use it for both.
2. **HTTPS redirect breaks non-proxied http environments** — the redirect fires on any request where `HTTPS=off` and `X-Forwarded-Proto != https`, which includes local/dev http with no TLS. Scope it to production (e.g. by host) or document that local must run under https/forwarded-proto to avoid a dead site.
3. **Canonical/OG URLs mix current-host and configured base** — `seo_meta_tags()` canonical defaults to `current_url()` (live host) while sitemap and JSON-LD use `site_base_url()` (the `site_url` setting). If the site is reachable on more than one host, canonical and structured-data URLs will disagree. Decide on one authoritative origin.
4. **Sitemap emitted after settings/DB errors still sends 200** — the per-query `try/catch` swallows failures silently; a broad DB outage yields a near-empty but 200-OK sitemap that could shrink Google's index view. Acceptable as fail-soft, but consider logging the caught throwable.
5. **`current_url()` trusts `HTTP_HOST`** — canonical and OG URLs are built from the client-supplied `Host` header, which is spoofable and can poison cached canonicals. Prefer deriving host from `site_url` for canonical/OG.
6. **Organization JSON-LD hardcodes contact/social data** — phone `+1 829 458 2170` and the Instagram URL are literals in `json_ld_organization()` rather than settings, so they drift from admin-managed data. Low priority; flag for consistency.

### Title built twice, brand appended twice

The layout computes a deduped visible title:

```php
$seoTitle = $pageTitle ?? $seoSiteName;
$seoFullTitle = (mb_stripos($seoTitle, (string)$seoSiteName) !== false)
    ? $seoTitle
    : $seoTitle . ' | ' . $seoSiteName;
```

Then it hands the *raw* `$seoTitle` (not `$seoFullTitle`) to the helper, which runs its own branding logic:

```php
$fullTitle = $title !== $siteName ? ($title . ' | ' . $siteName) : $siteName;
```

The two checks differ: the layout uses a case-insensitive substring match (`mb_stripos`), the helper uses exact inequality (`!==`). For the trip page, `pageTitle` is `$trip['meta_title'] ?: $trip['title']`. If an editor sets a `meta_title` like "Passeio Saona | Punta Cana para Brasileiros", the layout sees the brand already present and leaves `<title>` as-is — correct — but the helper's `$title !== $siteName` is true, so `og:title` becomes "Passeio Saona | Punta Cana para Brasileiros | Punta Cana para Brasileiros". The visible tab title is right while the shared/social title is doubled. Fix by threading `$seoFullTitle` through to the helper and having the helper treat the incoming title as final. (confirmed)

### HTTPS redirect: correct for proxy, hostile to plain http

```apache
RewriteCond %{HTTPS} off
RewriteCond %{HTTP:X-Forwarded-Proto} !https
RewriteRule ^ https://%{HTTP_HOST}%{REQUEST_URI} [L,R=301]
```

The `X-Forwarded-Proto !https` guard is the right defense against the redirect loop that happens when TLS is terminated at a proxy and the origin always sees `HTTPS=off` — behind such a proxy the header is present and the redirect is skipped, so no loop. That part is sound.

The exposure is any environment that genuinely serves http and neither terminates TLS upstream nor sets the forwarded header: local dev on `http://localhost`, or a plain-http staging box. There the condition is satisfied and Apache 301s to `https://<same-host>`, which fails if no cert/vhost answers on 443. This won't loop, but it makes the site unreachable. Scope the rule to the production host, or gate it behind an env flag. (confirmed)

The gzip and `mod_expires` blocks are wrapped in `IfModule`, so they no-op rather than 500 where the module is absent.

### Sitemap/robots depend on front-controller forwarding and schema columns

Every dynamic query was checked against the schema: `trips.status` is an ENUM that includes `'published'`; `trip_categories.slug` exists (the controller correctly doesn't filter it by a non-existent status); `blog_posts` has `slug`, `status`, `updated_at`; `pages` has `slug` and `status`. The emitted URL shapes (`/passeios/{slug}`, `/passeios/categoria/{slug}`, `/blog/{slug}`, `/pagina/{slug}`) all match registered routes.

Each query sits in its own `try/catch (\Throwable)`, so one missing table drops only its URL group and the rest of the sitemap stays well-formed. The tradeoff is silence: a broader DB failure produces a valid-but-thin sitemap returned with 200, and nothing is logged. For a document Google consumes to size its crawl, a swallowed error that shrinks the URL set is worth at least logging. (confirmed)

Serving works because the existing rewrite forwards anything that isn't a real file to `index.php`, and `/sitemap.xml` / `/robots.txt` are virtual. The handlers set `Content-Type` and `exit` before the layout renders, so no HTML leaks into the XML/text. (confirmed the `-f`/`-d` rewrite path in `.htaccess`.)

### Trip JSON-LD gates optional members to stay schema-valid

```php
if ($minPrice > 0) { $productLd['offers'] = [...]; }
$reviewCount = is_array($reviews) ? count($reviews) : 0;
if ($rating > 0 && $reviewCount > 0) { $productLd['aggregateRating'] = [...]; }
```

`offers` only appears with a real price, and `aggregateRating` requires both a positive rating and at least one review — this is what keeps the block from emitting the "AggregateRating with reviewCount 0" that Google flags as invalid. `$rating` comes from `getAverageRating()` (returns `float`) and `$reviews`/`$packages` are populated earlier in `show()`, so the string casts are safe. (confirmed)

Note the origin mismatch: `offers.url` and `Product.url` use `site_base_url()` while the page's own canonical (from `seo_meta_tags`) uses `current_url()`. If both hosts are live, structured-data URLs and canonical point at different origins. (confirmed — see Issues #3.)

### Google Analytics and page-specific JSON-LD injection

GA renders only when `trim(setting('google_analytics_id'))` is non-empty, so an unconfigured site emits no gtag. The block sits between custom CSS and `head_scripts`, and the page-specific `$jsonLd` is guarded by `!empty($jsonLd)`, so pages that don't set it emit only the global organization block. No collision with `head_scripts`/`body_scripts` (those still render from settings) or with the Google Translate widget, which lives at the end of `<body>` and is independent of the head metadata. (confirmed)
